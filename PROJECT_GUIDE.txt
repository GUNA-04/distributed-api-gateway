1. WHAT THIS PROJECT IS (THE 30-SECOND PITCH)
================================================================================

This is a production-style backend system that accepts e-commerce orders from
users and processes them asynchronously. It is split into two separate services
that communicate through a message broker:

    1. API GATEWAY  (FastAPI)  — the front door. Handles user registration,
       login (JWT tokens), order creation, and order lookups. It protects
       itself with a DISTRIBUTED RATE LIMITER and accepts orders even when
       downstream systems are slow.

    2. WORKER  (Kafka consumer) — the back office. Picks order events off a
       Kafka topic and processes them (simulated payment -> inventory ->
       shipping), with automatic retries and a dead-letter queue for orders
       that keep failing.

Between them sit three pieces of infrastructure:
    - PostgreSQL — the source of truth for users and orders
    - Redis      — the shared memory used by ALL gateway instances for rate
                   limiting (this is what makes the limiting "distributed")
    - Kafka      — the durable queue that decouples the gateway from the worker

WHY THIS ARCHITECTURE IS INTERESTING (the reason it impresses interviewers):

Imagine 10,000 users hit "Place Order" at the same time during a flash sale.

    NAIVE design:  The API handles the request AND charges the card AND
                   reserves stock AND prints shipping labels before responding.
                   Result: every request takes seconds, the API runs out of
                   connections, one slow payment provider stalls everything,
                   and a crash mid-way leaves half-done orders.

    THIS design:   The API validates the order, writes ONE row to Postgres,
                   publishes ONE event to Kafka, and responds in milliseconds:
                   "Order accepted, status PENDING". The payment/inventory/
                   shipping work happens later, in a separate, independently
                   scalable worker fleet. If the payment provider goes down,
                   orders pile up in Kafka (which never runs out of memory),
                   users see "PENDING", and nothing is lost. When the provider
                   recovers, the workers drain the backlog.

That single idea — decoupling acceptance from processing — is the foundation of
every large-scale system (Uber, Airbnb, Netflix all work this way). Everything
else in this project (rate limiting, idempotency, DLQ, autoscaling) exists to
make that idea safe in the real world.

3. THE BIG PICTURE: HOW THE WHOLE SYSTEM WORKS
================================================================================

                        +-------------------+
                        |      CLIENT       |
                        | (frontend/app/k6) |
                        +---------+---------+
                                  | HTTPS (with JWT in Authorization header)
                                  v
                        +-------------------+
                        |    AWS ALB or     |
                        |  local :8000      |        Load balancer (prod)
                        +---------+---------+
                                  |
                        +---------v---------+
                        |   GATEWAY (xN)    |   FastAPI app — gateway/app/
                        |  uvicorn workers  |   Each replica is identical.
                        +--+------+------+\ +
                           |      |      |
              +------------+      |      +--------------+
              v                   v                     v
        +-----------+     +--------------+     +---------------+
        |  REDIS    |     |  POSTGRES    |     |    KAFKA      |
        | rate-limit|     | users,orders |     | topic: orders |
        | sorted    |     | processed_   |     | (durable log) |
        | sets      |     | events,keys  |     +------+--------+
        +-----------+     +--------------+            |
                                                    consume (worker group)
                                                          |
                                                +---------v---------+
                                                |   WORKER (x1-10)  |
                                                |  worker/app/      |
                                                | payment -> stock  |
                                                | -> shipping       |
                                                +---------+---------+
                                                          |
                                                  writes result back to
                                                        POSTGRES

Key ideas to internalize:

*   STATELESS GATEWAY: the gateway keeps no session state in memory. A user's
    token is verified with a signature (no DB lookup needed for the signature
    itself), and shared state (rate limits) lives in Redis. That is why you can
    run 20 identical gateways behind a load balancer.

*   THE QUEUE IS THE CONTRACT: the gateway never talks to the worker directly.
    They only share the Kafka topic. You can restart, deploy, or crash either
    side without losing orders. This is called "loose coupling".

*   THE DATABASE IS THE TRUTH: an order exists (status PENDING) the moment the
    gateway commits it. Kafka messages can be redelivered, workers can crash —
    the row in Postgres is what the business trusts, and workers make it true
    ("this order is COMPLETED").

*   HORIZONTAL SCALING: gateway scales with CPU (more replicas), worker scales
    with backlog (number of unconsumed Kafka messages). They scale
    independently — that is the whole point of the queue.

4. THE REQUEST LIFECYCLE (FOLLOW ONE ORDER THROUGH THE SYSTEM)
================================================================================

Step-by-step, matching the actual code:

1)  POST /api/v1/auth/register  (gateway/app/api/v1/auth.py)
    - Pydantic validates the body (username >= 3 chars, valid email via
      email-validator, password >= 8 chars).
    - Passlib/bcrypt hashes the password (the hash, never the password, is
      stored).
    - A row is inserted into the `users` table.

2)  POST /api/v1/auth/login
    - Body is form-encoded (OAuth2 style, enables the Swagger "Authorize"
      button).
    - Password is verified with bcrypt.
    - Server creates a JWT: {"sub": "<user id>", "username": ..., "tier":
      "free", "exp": <30 min>} signed with SECRET_KEY (HS256).
    - Client stores the token and sends it as:
          Authorization: Bearer <token>

3)  POST /api/v1/orders  (gateway/app/api/v1/orders.py -> create_order)
    a. Middleware (gateway/app/main.py) assigns an X-Request-ID, starts a
       timer, and records Prometheus metrics.
    b. FastAPI parses the JWT from the header (gateway/app/core/security.py,
       get_current_user), loads the user from Postgres, and rejects the request
       with 401 if the token is invalid/expired.
    c. Rate limiter (gateway/app/services/rate_limiter.py) asks Redis:
       "how many requests has this user made to /api/v1/orders in the last
       60 seconds?" Free tier = 100/min. Over the limit -> HTTP 429 with a
       Retry-After header.
    d. If the request carries an X-Idempotency-Key, the gateway first looks for
       an order that already used it and, if found, returns the ORIGINAL
       response (this makes client retries safe).
    e. The order row is inserted into Postgres with status PENDING
       (a unique constraint on idempotency_key makes duplicate inserts
       impossible even under concurrency).
    f. The event id is claimed in the processed_events table
       (gateway/app/services/idempotency.py) with INSERT ... ON CONFLICT
       DO NOTHING.
    g. An event is published to the Kafka topic `orders`, keyed by order id
       (gateway/app/services/kafka_producer.py). Keying by order id guarantees
       all events for one order land on the same partition, in order.
    h. Response (HTTP 201):
          {"order_id": "...", "status": "PENDING",
           "message": "Order created and queued for processing"}

4)  WORKER (worker/app/consumer.py)
    a. The worker is in consumer group "order-processor-group" and subscribes
       to topics `orders` and `orders.retry`.
    b. It polls Kafka in batches (up to 50 records, 1s timeout), processes all
       messages in a batch concurrently (asyncio.gather), and ONLY THEN
       commits the offsets. Manual commits = no order is ever lost if the
       worker dies mid-batch (Kafka will redeliver).
    c. For each message, OrderProcessor (worker/app/processor.py):
       - checks processed_events — was this event already handled? (duplicate
         protection after redelivery)
       - loads the order, sets status PROCESSING
       - runs the three business steps (simulated): payment -> inventory ->
         shipping
       - sets status COMPLETED and records processed_at
       - marks the event processed
    d. On failure: handle_failure() increments retry_count, stores the error on
       the order row, and either re-publishes to `orders.retry` (retry 1 or 2)
       or `orders.dlq` (after MAX_RETRIES = 3), marking the order
       DEAD_LETTERED.

5)  GET /api/v1/orders/{id}
    - Returns the current status. The user polls this to watch their order go
      PENDING -> PROCESSING -> COMPLETED.

Data flow summary:
    CLIENT -> GATEWAY -> [Postgres row + Kafka event] -> WORKER -> Postgres
    (the gateway response and the worker processing are two independent worlds
     connected only by the queue)

5.1 PYTHON (3.10) AND ASYNCIO
--------------------------------------------------------------------------------
WHAT: Python is the language. asyncio is Python's mechanism for concurrency in
a single thread: while one task waits for I/O (a database query, a Kafka
publish), the event loop runs another task. One async process can therefore
hold thousands of in-flight requests, because the bottleneck is waiting, not
CPU.

WHY HERE: an API gateway is 99% waiting on I/O (DB, Redis, Kafka, network).
Threads would work but are expensive (each thread = ~MB of stack + OS
scheduling). async lets one uvicorn process juggle thousands of connections.

Mental model:
    def sync_work():       -> one waiter per waiter (blocking, needs threads)
    async def async_work() -> waiters get a pager; one worker serves them all

The rules that matter:
*   `async def` defines a coroutine; you must `await` it.
*   Never call blocking code (time.sleep, requests, psycopg2) inside async code
    — it freezes the whole event loop. Use the async versions (asyncio.sleep,
    httpx.AsyncClient, asyncpg).
*   `asyncio.gather(*tasks)` runs coroutines concurrently and returns when all
    finish — used by the worker to process a batch in parallel
    (worker/app/consumer.py, run()).
*   `async with` = async context manager (acquire/release resources without
    blocking) — used for DB sessions everywhere.
*   `@asynccontextmanager` + FastAPI `lifespan` = code that runs at startup and
    shutdown of the app (connect Postgres/Redis/Kafka; disconnect on the way
    out) — gateway/app/main.py.

KEY POINTS TO REMEMBER:
- async is CONCURRENCY (juggling), not PARALLELISM (more hands). CPU-heavy work
  still needs processes/threads.
- One blocked call in async code blocks EVERYTHING — that's the #1 async bug.
- async/await in this codebase is why "500+ RPS on one small machine" is even
  possible.

5.2 FASTAPI — THE WEB FRAMEWORK (gateway/app/)
--------------------------------------------------------------------------------
WHAT: a modern Python web framework built on standard Python type hints,
running on the ASGI standard. Starlette does the HTTP work, Pydantic does the
data work, FastAPI glues them together.

WHY HERE: fastest way to write correct APIs in Python, and it generates
interactive docs automatically (visit http://localhost:8000/docs).

Features used here, and what they do:
*   Path operations with decorators:
        @router.post("", status_code=201)          (orders.py)
    The function runs for that method+path. `status_code` sets the success
    status (201 = created, NOT 200 — a real-world correctness detail).
*   Dependency injection with Depends: `db: AsyncSession = Depends(get_db)`.
    FastAPI calls get_db() per request and injects the result. Dependencies can
    be overridden in tests (see test_orders_flow.py) — this is why the test
    suite can fake the database.
*   Security via HTTPBearer (core/security.py): extracts the token from the
    Authorization header; get_current_user validates it and loads the user.
*   Pydantic request/response models (schemas/order.py): incoming JSON is
    parsed and validated automatically (wrong types/missing fields -> 422 with
    a precise error list). response_model also FILTERS output, so internal
    fields never leak.
*   Middleware (@app.middleware("http") in main.py): every request passes
    through it — used to add X-Request-ID, measure latency, count metrics.
*   Routers (APIRouter) keep endpoints modular: /auth, /orders, /health.
*   Lifespan events for startup/shutdown.

KEY POINTS TO REMEMBER:
- FastAPI = Starlette (async HTTP) + Pydantic (validation) + DI + OpenAPI.
- 422 = validation failed; 401 = not authenticated; 403 = authenticated but
  forbidden; 409 = conflict (duplicate); 429 = rate limited; 201 = created.
- "Dependency injection" sounds fancy: it just means the framework hands your
  function its dependencies so you can swap them in tests.

5.3 PYDANTIC + PYDANTIC-SETTINGS
--------------------------------------------------------------------------------
WHAT: Pydantic validates and serializes data using type hints. A BaseModel
declares the shape of the data; Pydantic enforces it and converts types
(e.g. the JSON string "129.99" becomes a Decimal(129.99)).

WHERE: common/app/schemas.py (Kafka event models), gateway/app/schemas/order.py
(API request/response models), common/app/config.py (Settings).

Details worth knowing:
*   Field(..., gt=0) — `...` means REQUIRED, gt=0 means "greater than 0" (no

*   EmailStr needs the email-validator package (now in requirements.txt) and

*   model_dump(mode="json") converts Pydantic values (Decimal, datetime) into

*   pydantic-settings (config.py): Settings reads environment variables and an
    optional .env file into one typed object, cached with @lru_cache so the

    configuration: same code, different config per environment.

KEY POINTS TO REMEMBER:
- Pydantic = validation + serialization + docs, all from type hints.
- v2 is Rust-powered (pydantic-core) and much faster than v1.
- Settings class = all configuration in one auditable place.

5.4 POSTGRESQL + SQLALCHEMY 2.0 (ASYNC) + ASYNCPG
--------------------------------------------------------------------------------
WHAT: PostgreSQL is the relational database — the system of record. SQLAlchemy
is Python's ORM (Object-Relational Mapper): you write Python classes
(gateway/app/models/database.py) and it generates SQL. asyncpg is the raw async
driver that actually speaks Postgres' wire protocol.

WHY POSTGRES (vs MySQL/MongoDB):
- ACID transactions: order creation = several related writes; either all
  happen or none.
- JSONB: semi-structured `items` column with indexing — relational + document
  in one database.
- Rich types used here: UUID primary keys, NUMERIC(12,2) for money (NEVER use
  floats for money — 0.1 + 0.2 != 0.3), TIMESTAMPS, partial composite indexes.
- Battle-tested for financial data.

HOW THE LAYERS STACK (important for interviews):
    your code -> SQLAlchemy ORM (session, models) -> asyncpg driver -> Postgres
    The session (gateway/app/db/session.py) is your window into a transaction:
    - async_sessionmaker builds sessions from a POOL of reusable connections
      (opening a TCP+auth connection per request would be brutally slow).
    - pool_size=20, max_overflow=10: at most 30 connections; beyond that,
      requests WAIT (pool_timeout) instead of crashing Postgres.
    - pool_pre_ping=True: check a connection is alive before using it (heals
      dropped connections).
    - expire_on_commit=False: objects stay usable after commit (async-friendly;
      avoids extra round trips).

MODELS (gateway/app/models/database.py):
- Order        — the order row: money, status, items JSONB, idempotency_key
                 (UNIQUE — the DB-level duplicate protection), correlation_id,
                 retry_count, error_message, created/updated/processed_at.
- User         — credentials (bcrypt hash), tier for rate limits.
- ProcessedEvent — idempotency table: every handled event id + a TTL timestamp
                 so old entries can be cleaned up.
- APIKey       — schema for programmatic access (implemented in SQL, not yet in
                 the API — honest scope boundary).

INDEXES — a real performance topic in this repo:
- ix_orders_user_created (user_id, created_at) powers "my orders, newest first".
- ix_orders_created_status powers worker analytics queries.
- Index rule of thumb: index the columns you filter/sort/join on, not
  everything (indexes slow writes).

KEY POINTS TO REMEMBER:
- ORM != database. Know both: the ORM for speed of development, SQL to know
  what actually runs.
- Connection pooling is what makes high RPS possible.
- NUMERIC for money. UUIDs for IDs (no sequential guessing, safe to expose).
- transactions: db.commit() = make it permanent; db.rollback() = undo on error
  (see get_db in session.py — it rolls back automatically if your endpoint
  raises).

5.5 REDIS — DISTRIBUTED RATE LIMITING (gateway/app/services/rate_limiter.py)
--------------------------------------------------------------------------------
WHAT: Redis is an in-memory data store (microsecond reads/writes). It is used
here as SHARED MEMORY between all gateway instances. Each instance keeps its
own counters in RAM, but rate limiting must be GLOBAL — if user X may send 100
requests/min and there are 5 gateway replicas, X must be limited to 100/min
TOTAL, not 500.

THE DATA STRUCTURE THAT MAKES IT WORK: the SORTED SET (ZSET).
- A ZSET stores members with a numeric score, ordered by score.
- Here: member = unique request id, score = request timestamp.
- Sliding window algorithm (is_allowed in rate_limiter.py):
    1. ZREMRANGEBYSCORE key 0 (now - window)   # drop entries older than 60s
    2. ZCARD key                               # how many requests remain
    3. if count >= limit            -> 429 Too Many Requests
    4. ZADD key (uuid, now)         # record this request
    5. EXPIRE key window+1          # safety net so abandoned keys die
  The window "slides" because we always prune by timestamp, not by fixed
  calendar minutes. Compare with the naive "fixed window" (counters reset at
  :00) which allows 2x bursts around the boundary. Sliding window log is the
  most accurate strategy; sliding window counter and token bucket are cheaper
  approximations.

TIERED LIMITS (get_limit_tier): free=100/min, basic=1000, premium=5000,
enterprise=50000. The user's tier comes from the JWT claim. Real products
monetize exactly this way.

WHERE ELSE REDIS FITS IN PRODUCTION: caching hot reads, session storage, job
queues, distributed locks. Same database, many uses.

KEY POINTS TO REMEMBER:
- "Distributed" rate limiting = state in Redis, not in the app.
- ZSET + timestamps = sliding window; know the 5 commands above.
- 429 + Retry-After is the correct HTTP behavior (see check_rate_limit).

5.6 APACHE KAFKA — THE BACKBONE (gateway/app/services/kafka_producer.py,
    worker/app/consumer.py)
--------------------------------------------------------------------------------
WHAT: Kafka is a distributed, durable, append-only LOG (not just a queue).
Producers append records to the end of a TOPIC; consumers read them at their
own pace using OFFSETS (a bookmark: "I have read up to record #4,317").

THE VOCABULARY YOU MUST OWN:
- Broker        — a Kafka server. A cluster has many.
- Topic         — a named log, e.g. `orders`. This project creates three:
                  orders, orders.retry, orders.dlq.
- Partition     — a topic is split into partitions (6 here) for parallelism and
                  scale. Records with the SAME KEY go to the SAME partition, so
                  per-key order is guaranteed. (Key = order id here.)
- Offset        — position within a partition. Consumers commit offsets to
                  record progress.
- Consumer group — many workers sharing the work: each partition is consumed by
                  exactly ONE member of the group. Add workers -> Kafka
                  rebalances partitions between them. This IS the horizontal
                  scaling story (this project: group "order-processor-group").
- Producer acks — acks="all" means the broker confirms only after the record is
                  persisted (with replication). Safest setting; used here.
- Retention     — messages are NOT deleted on read. They stay (24h config in
                  docker-compose) so consumers can be rewound/replayed. This is
                  Kafka's superpower vs a classic queue (RabbitMQ/SQS delete on
                  read).

WHY KAFKA (vs just calling the worker or using Celery/RabbitMQ):
- DURABILITY: broker crash does not lose accepted orders (replicated log).
- BACKPRESSURE for free: worker down? Messages pile up on disk. Traffic spike
  100x? Workers drain at their own pace. The gateway never blocks.
- REPLAY: fix a bug in the worker, rewind the offset, reprocess yesterday.
- FAN-OUT: today one worker consumes `orders`; tomorrow an analytics service
  can consume the SAME topic independently.
- ORDERING where it matters: per-partition (per order-id) ordering.

THE CRITICAL DELIVERY SEMANTICS (interviewers love this):
- AT-LEAST-ONCE (what this project implements): the worker commits offsets
  AFTER processing. If it crashes before committing, Kafka redelivers — no
  message is lost, but some may be processed twice.
- AT-MOST-ONCE: commit before processing — never duplicated, but can be lost.
- EXACTLY-ONCE: the dream; needs transactional producers/idempotent consumers.
- Because at-least-once means "sometimes twice", EVERY consumer MUST be
  idempotent — which is exactly why ProcessedEvent exists (section 9). The pair
  (at-least-once delivery + idempotent processing) is the industry-standard way
  to get exactly-once EFFECTS.

AIOKAFKA specifics used here:
- Producer: enable_idempotence=True (broker de-dupes producer retries),
  compression_type="gzip", linger_ms=10 (batch tiny waits for bigger, cheaper
  batches), send_and_wait() = publish + await broker ack.
- Consumer: enable_auto_commit=False (manual commit AFTER the batch — the
  at-least-once guarantee), auto_offset_reset="earliest" (start from the
  beginning if no offset exists yet), getmany() for batch polling.
- GOTCHA you saw fixed in section 12: aiokafka's producer has NO `retries=`
  argument (that is the kafka-python library's API). Passing it crashed
  producer startup, which silently degraded the gateway.

KEY POINTS TO REMEMBER:
- Kafka = durable, replayable, partitioned log; offset bookmarks; consumer
  groups = parallelism.
- Key by order id for per-order ordering.
- Manual offset commit after processing = at-least-once; pair with idempotent
  consumer = exactly-once effects.
- Queue full? It's on disk. That is the backpressure story.

5.7 JWT AUTHENTICATION + BCRYPT (gateway/app/core/security.py)
--------------------------------------------------------------------------------
WHAT: JSON Web Token — a signed JSON payload. Server issues
{"sub": user_id, "exp": expiry, "tier": "free"} signed with SECRET_KEY. On
every request, the server only needs to CHECK THE SIGNATURE (no DB hit) to
know who you are and what the claims are.

ANATOMY: header.payload.signature (base64url, dots between). The payload is
READABLE by anyone (base64 is not encryption!) — it is TAMPER-PROOF, not
secret. Never put a password in a JWT.

FLOW IN THIS PROJECT:
- register: bcrypt hash (password NEVER stored in plain text; bcrypt is
  deliberately slow + salted so rainbow/brute-force attacks are expensive).
- login: verify password -> issue JWT (30 min expiry, HS256).
- every protected endpoint: HTTPBearer extracts the header, decode_token
  validates signature + expiry; get_current_user loads the fresh User row (so
  a deactivated user is rejected even with a valid token).

WHY HS256 HERE: one shared secret, simplest. Production multi-service setups
often use RS256 (private key signs, public key verifies — other services can
verify without holding the signing key).

THE BUG CLASS YOU HIT (and fixed): passlib 1.7.4 + bcrypt >= 4.1 are
incompatible (passlib reads bcrypt.__about__ which was removed). Symptom:
ValueError on hashing -> login/register 500s. Fix: pin bcrypt==4.0.1.
Real-world lesson: version pinning matters; read the deprecation logs.

KEY POINTS TO REMEMBER:
- JWT = signed claims; verify with signature only; carry expiry ALWAYS.
- bcrypt = slow + salted password hashing. Never MD5/SHA for passwords.
- 401 (who are you?) vs 403 (I know you — no).
- Access tokens short-lived; refresh tokens are the natural next feature.

5.8 DOCKER + DOCKER COMPOSE (infra/docker/)
--------------------------------------------------------------------------------
WHAT: Docker packages an app + its dependencies into an IMAGE that runs
identically anywhere. Compose orchestrates MULTIPLE containers on one machine
with one command and a YAML file.

IN THIS PROJECT (infra/docker/docker-compose.yml):
- postgres:16-alpine with tuned memory settings, healthcheck (pg_isready), and
  scripts/init_db.sql auto-executed on first start (creates tables, indexes,
  triggers, seed user).
- redis:7-alpine with maxmemory + allkeys-lru eviction policy.
- zookeeper + kafka (Confluent images) with dual listeners (kafka:29092 inside
  the docker network, localhost:9092 from the host — the #1 Kafka/Docker
  gotcha, since brokers ADVERTISE their address to clients).
- kafka-init one-shot container that creates the 3 topics, then exits.
- gateway + worker images built from Dockerfile.gateway / Dockerfile.worker,

7. CORE PATTERN #1: DISTRIBUTED RATE LIMITING (DEEP DIVE)
================================================================================

THE PROBLEM: protect the system from abusive users, runaway scripts, and
accidental DDoS-by-bug. In a multi-instance deployment, in-memory counters are
useless — each instance only sees 1/N of the traffic.

THE SOLUTION HERE (rate_limiter.py + Redis ZSETs), and the five commands:

    key = ratelimit:{endpoint}:{user_id}
    1) ZREMRANGEBYSCORE key 0 (now - window)    # forget requests older than 60s
    2) ZCARD key                                # count requests still in window
    3) count >= limit ?                         # free: 100/min
           return 429 + Retry-After
       else:
    4) ZADD key (uuid(), now)                   # remember this request
    5) EXPIRE key window+1                      # keys die if user walks away

WHY SORTED SETS: they give you "count how many scores fall in a range" and
"delete scores in a range" in O(log N), atomically, in a single shared store.
It's the canonical Redis rate-limiting pattern (Redis docs themselves teach
it).

THE ALGORITHM FAMILY (know the trade-offs):
- Fixed window counter: 1 INCR + EXPIRE. Cheapest; allows 2x burst at window
  boundaries (99 requests at 00:59 + 99 at 01:00 = 198 in 2 seconds).
- Sliding window log (THIS PROJECT): exact, but stores one entry per request.
- Sliding window counter / token bucket: approximate but memory-light; token
  bucket also allows controlled bursts (used by Stripe, GitHub API).

DESIGN DETAILS WORTH MENTIONING IN AN INTERVIEW:
- Limits are per (user, endpoint) and per TIER — product logic enforced by
  infrastructure.
- The limiter runs as a normal await inside the endpoint, so responses can
  carry X-RateLimit-* headers and 429 with Retry-After (check_rate_limit).
- Rate-limit metrics (gateway_rate_limited_total) show abuse attempts live.
- Failure mode: if Redis dies, the gateway can fail open (allow) or closed
  (block) — a deliberate availability/consistency trade-off you should be
  ready to discuss.

8. CORE PATTERN #2: EVENT-DRIVEN PROCESSING WITH KAFKA (DEEP DIVE)
================================================================================

WHY A QUEUE AT ALL? Synchronous processing couples availability and latency:
payment provider slow => your API is slow => your users retry => you fall over.
Asynchronous processing converts "do this now" into "record this happened".
The API's SLA becomes milliseconds; the business SLA becomes seconds.

EVENTS VS COMMANDS: the Kafka message is an EVENT ("ORDER_CREATED for order X,
here is the data") — a fact that already happened. Workers react to facts.
This framing (event-driven architecture / EDA) is what the whole design is
called.

THE PRODUCER SIDE (kafka_producer.py):
- JSON-serializes events; key = order id => same partition => per-order order.
- acks="all" + enable_idempotence=True: broker-side protection against
  duplicates from producer retries (so publishing retries are safe).
- send_and_wait returns only when the broker has persisted the record.
- If Kafka is unreachable, the ORDER IS STILL STORED (row already committed)
  and the failure is counted in gateway_orders_queue_failed_total — graceful
  degradation, honest telemetry. (A repair job re-publishing unqueued orders
  is a natural "next step" to mention.)

THE CONSUMER SIDE (consumer.py):
- subscribes to `orders` AND `orders.retry` (retries re-enter the same pipe).
- loop: getmany(max_records=50, timeout 1s)
        -> asyncio.gather over all messages (concurrency inside the batch)
        -> consumer.commit() AFTER the batch finishes (manual commit!).
- If the worker dies mid-batch: offsets were NOT committed => Kafka redelivers
  to the next worker => no order lost. Combined with the ProcessedEvent
  duplicate check, redelivery is harmless. (at-least-once + idempotency)
- Graceful shutdown: SIGTERM/SIGINT stop the loop; in-flight work completes;
  connections close cleanly (this is what ECS sends on deploys).

SCALING: 6 partitions => up to 6 workers in one group do useful work in
parallel; more workers than partitions just idle (interview gotcha!).

9. CORE PATTERN #3: IDEMPOTENCY (DEEP DIVE)
================================================================================

THE PROBLEM: networks retry. Users double-click. Kafka redelivers. A "create
order" is not idempotent by nature: two identical POSTs = two orders = real
money. You must make "do it twice" behave like "do it once".

THE CLIENT CONTRACT: the client sends a unique key with the request:
        X-Idempotency-Key: <uuid or hash>
(Stripe made this pattern famous.) The same key + same request must return the
same result, not create a second resource.

THE THREE LAYERS IN THIS PROJECT (defense in depth):

LAYER 1 — FAST PATH (orders.py): before doing anything, look up
          SELECT ... WHERE idempotency_key = :key. Found? Return the ORIGINAL
          201 response. Client retries become harmless.

LAYER 2 — DATABASE UNIQUE CONSTRAINT (models/database.py):
          idempotency_key column has UNIQUE. Even if two identical requests
          race (both pass layer 1 before either commits), the second INSERT
          fails with IntegrityError -> handled -> 409. Constraints are the ONLY
          thing that stays correct under true concurrency — application checks
          are best-effort.

LAYER 3 — PROCESSED-EVENTS TABLE (idempotency.py):
          INSERT INTO processed_events (event_id, ...) ON CONFLICT (event_id)
          DO NOTHING RETURNING event_id
          - row returned  => fresh claim (not a duplicate)
          - no row        => someone already claimed it (duplicate)
          One atomic statement = race-safe "check and claim" without explicit
          locks. The worker uses the same table (different event ids) to make
          Kafka redeliveries harmless.

ORDER OF OPERATIONS MATTERS (a bug found here): claiming the event BEFORE
inserting the order means a failed insert burns the key for 24h (client retry
-> 409 with no order to show). The fixed flow inserts the order FIRST, then
claims the event. Think about which failure modes your ordering creates.

GENERAL RULE: every state-changing API that can be retried (payments! order
creation!) needs idempotency keys; every queue consumer needs dedup.
"Exactly-once effects from at-least-once delivery" is the phrase to remember.

================================================================================
10. CORE PATTERN #4: RETRIES + DEAD LETTER QUEUE (DEEP DIVE)
================================================================================

FAILURES ARE NORMAL: payment provider 500s, DB blips, timeouts. The question
is not "will it fail?" but "what happens after?".

THE PIPELINE (worker/app/processor.py, handle_failure):
    attempt fails
      -> retry_count += 1, error_message stored on the order row
      -> retry_count < 3  ?  publish to orders.retry   (try again later)
                           : publish to orders.dlq     (give up HUMANLY)
                             order status = DEAD_LETTERED

THE DLQ IS NOT A GRAVEYARD — it is a parking lot for a human/automation to
inspect: is the message malformed (poison message)? Was the provider down?
Fix the cause, then REPLAY the messages. Without a DLQ, failed messages
either vanish or block the pipeline forever (head-of-line blocking).

BACKOFF: immediate retries hammer a struggling provider (retry storm). Real
systems use exponential backoff with jitter (1s, 2s, 4s... + randomness).
This repo's retry topic + common/app/config.py (MAX_RETRIES, RETRY_DELAY_SECONDS)
is the hook where that scheduling lives — extending it is a great exercise.

OBSERVABILITY OF FAILURES: every failure is visible twice — on the order row
(retry_count, error_message — queryable for support) and in logs/metrics.
"State the error on the entity" is a pattern in itself.

11. CORE PATTERN #5: OBSERVABILITY (DEEP DIVE)
================================================================================

YOU CANNOT OPERATE WHAT YOU CANNOT SEE. Three pillars, all present:

1) STRUCTURED LOGS (logging_config.py): every line is JSON with timestamp,

12. BUGS THAT WERE FOUND AND FIXED (WAR STORIES — LEARN FROM EACH ONE)
================================================================================

These are real bugs that were present in this codebase and are now fixed.
Each one is a lesson, and each is a great interview story ("tell me about a
hard bug you fixed").

1)  DUPLICATED ORDER-INSERT BLOCK (gateway/app/api/v1/orders.py)
    SYMPTOM: would have inserted every order TWICE; with an idempotency key
    the second insert violated the UNIQUE constraint -> 500 on every order.
    CAUSE: copy-paste block left in the endpoint.
    LESSON: endpoints doing multi-step writes deserve scrutiny; tests with a
    REAL database catch this class instantly.

2)  INVERTED IDEMPOTENCY CHECK (gateway/app/services/idempotency.py)
    SYMPTOM: check_processed returned True for fresh inserts and False for
    duplicates — every new order would get 409 Conflict; real duplicates
    sailed through. The docstring and the code disagreed.
    CAUSE: RETURNING semantics misread — INSERT ... ON CONFLICT DO NOTHING
    RETURNING returns a ROW for a fresh insert and NO ROW for a duplicate;
    the code did `fetchone() is not None` where it needed `is None`.
    LESSON: SQL RETURNING semantics are subtle; write a test that pins the
    contract (test_idempotency.py now does exactly that).

3)  KAFKA PRODUCER NEVER STARTED (gateway/app/services/kafka_producer.py)
    SYMPTOM: gateway logged "Kafka not available ... got an unexpected keyword
    argument 'retries'" and ran in degraded mode forever — no order was EVER
    queued; the worker sat idle.
    CAUSE: aiokafka's AIOKafkaProducer has no `retries=` parameter (that is
    the kafka-python library's API — the two libraries were mixed up).
    FIX: removed the argument (aiokafka retries internally);
    enable_idempotence covers producer retry safety.
    LESSON: "silent degradation" needs an alert. /health now shows kafka:
    healthy, and the E2E run proves events flow.

4)  DECIMAL IS NOT JSON-SERIALIZABLE (orders.py + JSONB)
    SYMPTOM: first real order insert blew up with
    "Object of type Decimal is not JSON serializable" (HTTP 500).
    CAUSE: Pydantic parses "unit_price": "129.99" into a Decimal; model_dump()
    kept Decimals inside the items dict; asyncpg's JSON serializer refused.
    FIX: item.model_dump(mode="json") — Pydantic converts Decimal/datetime to
    JSON-safe primitives before the JSONB write.
    LESSON: types that are fine in Python (Decimal) are not fine in JSON.
    Money stays Decimal in the DB (NUMERIC) and becomes a string only in JSON.

5)  IDEMPOTENCY KEY BURNED ON FAILED INSERT (orders.py ordering)
    SYMPTOM: the event-id claim happened BEFORE the order insert; if the
    insert failed (see bug 4), the key stayed claimed for 24h — client retry
    with the same key got 409 even though no order existed.
    FIX: insert order first (UNIQUE constraint protects), claim the event
    after a successful commit.
    LESSON: order of side effects defines your failure modes; think "what if
    we crash between step 2 and step 3?" for every sequence.

6)  PASSLIB/BCRYPT VERSION CONFLICT (requirements.txt)
    SYMPTOM: hash_password() raised "ValueError: password cannot be longer
    than 72 bytes" during passlib's internal backend probe; registration and
    login 500'd.
    CAUSE: passlib 1.7.4 is unmaintained and incompatible with bcrypt >= 4.1.
    FIX: pin bcrypt==4.0.1.
    LESSON: read the warning logs ("error reading bcrypt version" was there
    all along); pin transitive dependencies that break at runtime.

7)  HEALTH CHECK ALWAYS "unhealthy" (gateway/app/api/v1/health.py)
    SYMPTOM: DB status always reported unhealthy even when Postgres was fine.
    CAUSE 1: session.execute("SELECT 1") — SQLAlchemy 2.0 requires
    text("SELECT 1"); a raw string raises ArgumentError.
    CAUSE 2: health.py did `from gateway.app.main import redis_client`, which
    binds the VALUE at import time (None) — the client assigned later during
    lifespan was never seen. Fixed by moving the client into a dedicated
    module (services/redis_client.py) that owns its state.
    LESSON: Python's `from x import y` copies the reference ONCE. For mutable
    module state, import the module or a getter. Also: a health endpoint that
    lies is worse than none.

8)  UUID STRING BIND ERRORS (security.py, processor.py)
    SYMPTOM: comparing a UUID column to a raw string works on some drivers but
    asyncpg rejects it at bind time.
    FIX: uuid.UUID(value) conversion before queries/writes.
    LESSON: the DB driver is the source of truth for what it accepts; don't
    rely on implicit coercion.

9)  LOGIN 403 AFTER REGISTER (auth.py + model defaults)
    SYMPTOM: freshly registered user could not log in ("Account is inactive").
    CAUSE: is_active relies on a FLUSH-TIME default — the in-memory object has
    None until it round-trips the DB; login checked the attribute.
    FIX: set is_active=True explicitly at registration.
    LESSON: ORM defaults are applied at INSERT, not at construction; code
    touching an object pre-flush must not assume defaults exist.

10) LOAD TEST LOGIN USED QUERY PARAMS (loadtest/locust/order_load_test.py)
    SYMPTOM: every virtual user failed to get a token (endpoint expects FORM
    data; the script sent ?username=...&password=...).
    FIX: data= instead of params=.
    LESSON: your load tests are code too — a broken load test gives you
    confident wrong numbers. Also note: credentials in query strings end up in
    logs — never do that in production.

META-LESSON: the original 12 tests passed while the app was completely broken
(1, 3, 4 would have failed on first real use). Mocks verify LOGIC; only real
infrastructure verifies INTEGRATION. Every layer of the testing pyramid exists
because the others are blind to something.

15. KEY POINTS TO REMEMBER (THE ONE-PAGE CHEAT SHEET)
================================================================================

ARCHITECTURE
 * Two services, one queue: gateway (accept) + worker (process). The queue is
   the contract; neither knows the other exists.
 * Gateway is stateless -> scale horizontally. Worker scales with backlog.
 * Postgres is the truth; Kafka is the pipe; Redis is the shared memory.

HTTP STATUS CODES USED (know why each exists)
 * 201 created (order/user)  * 200 ok  * 401 bad/missing token
 * 403 inactive account      * 404 not found (or not yours — no data leak)
 * 409 duplicate/conflict    * 422 validation failed  * 429 rate limited
 * 503 not ready (readiness probe)

SECURITY
 * bcrypt for passwords (slow + salted), JWT (30 min, HS256) for sessions.
 * The JWT payload is readable, not encrypted — tamper-proof only.
 * Tier from the JWT drives rate limits; is_active is re-checked from DB.

DATA
 * NUMERIC for money, never float. UUID PKs. JSONB for flexible items.
 * UNIQUE(idempotency_key) is the concurrency-proof duplicate guard.
 * Indexes: (user_id, created_at) for "my orders"; status/created for ops.

REDIS RATE LIMITER = 5 ZSET COMMANDS (memorize)
 ZREMRANGEBYSCORE -> ZCARD -> (limit?) -> ZADD -> EXPIRE

KAFKA
 * Key = order_id -> same partition -> per-order ordering.
 * enable_auto_commit=False + commit AFTER processing = at-least-once.
 * Idempotent consumer (ProcessedEvent) turns at-least-once into
   exactly-once effects.
 * 6 partitions -> max 6 parallel consumers per group.
 * Retry topic then DLQ after MAX_RETRIES=3; DLQ is for humans to fix+replay.

IDEMPOTENCY
 * Client: X-Idempotency-Key. Server: fast-path lookup, DB UNIQUE constraint,
   atomic ON CONFLICT claim. Claim AFTER the order insert succeeds.

TESTING
 * Unit (mocks) -> integration (in-process app + fakes) -> E2E (real stack)
   -> load (Locust/k6). Percentiles over averages; P95/P99 are the truth.
 * A green test suite is not a working product — the original suite passed
   while the app was broken.

OPS
 * /health (deep), /health/live (alive?), /health/ready (traffic?),
   /metrics (Prometheus). JSON logs with request_id everywhere.
 * Graceful shutdown matters: ECS/K8s send SIGTERM on every deploy.

16. INTERVIEW QUESTIONS AND STRONG ANSWERS
================================================================================

Q: Walk me through what happens when a user places an order.
A: JWT is validated, per-user rate limit checked in Redis, duplicate check on
   the idempotency key, order row inserted with status PENDING (unique
   constraint prevents duplicates under concurrency), event published to Kafka
   keyed by order id, HTTP 201 returns immediately. The worker consumes the
   event, marks PROCESSING, runs payment/inventory/shipping, marks COMPLETED,
   and records the event id so redeliveries are skipped. Total user-perceived
   latency: one Postgres insert + one Kafka ack.

Q: Why Kafka and not just doing the work in the API, or Celery/RabbitMQ?
A: Doing the work synchronously couples my availability to the payment
   provider's and turns user latency into seconds. Of the async options,
   Kafka's log gives replay (rewind offsets after a bug fix), fan-out (many
   independent consumers of one topic), and disk-backed backpressure (a
   traffic spike becomes storage, not an outage). RabbitMQ/Celery are great
   for task queues, but Kafka is the better fit for an event stream that
   analytics might also consume.

Q: What happens if the worker crashes mid-processing?
A: Offsets are committed only after a batch finishes, so unprocessed messages
   are redelivered to the remaining workers (at-least-once). The consumer is
   idempotent — the ProcessedEvent table (and the order's own status) makes
   redelivery a no-op. No loss, no double-charging.

Q: What happens if two identical requests arrive at the same time?
A: Both pass the fast-path SELECT (neither is committed yet), but the
   idempotency_key UNIQUE constraint lets exactly one INSERT succeed; the
   loser gets IntegrityError -> 409. That's why the constraint, not the
   application check, is the real guarantee.

Q: How does the rate limiter work, and why Redis?
A: A sliding-window log: per (user, endpoint) sorted set of request
   timestamps. Prune older than the window, count what's left, add the current
   request, expire the key. It must be Redis (not app memory) because N
   gateway replicas must share ONE limit per user.

Q: How would you scale this 10x?
A: Gateway: more replicas behind the ALB (stateless; Redis/DB pools per
   instance tuned). Worker: more consumers — Kafka spreads partitions across
   the group (up to 6 here; increase partitions to go beyond). Postgres: read
   replicas + right-sized indexes; hot rows would move to Redis caching.
   Redis: cluster mode. All of this is why each piece is stateless/swappable.

Q: What would you build next?
A: (Pick two or three, sound opinionated:) a re-publisher that re-queues
   orders stored-but-not-queued (the queue-failure metric detects them);
   real payment provider integration with exponential backoff scheduling on
   the retry topic; Alembic migrations replacing create_tables.py; refresh
   tokens; a Prometheus alert rule on gateway_orders_queue_failed_total.

Q: What was the hardest bug?
A: Tell bug #3 (Kafka producer never started due to a wrong library argument,
   masked by silent degradation) — then explain the fix AND the process lesson
   (degraded modes need alarms; E2E beats mocks). Or bug #4 (Decimal in JSONB)
   to show depth in serialization layers. Owning the process lesson is what
   scores points, not the bug itself.

Q: What are the system's weaknesses? (asked to see honesty)
A: The rate limiter stores one entry per request (memory-hungry at scale — a
   token bucket would be cheaper); retries are immediate rather than
   backoff-scheduled; there is exactly one Kafka broker and one Postgres in
   docker (no replication locally); passlib is unmaintained and should become
   argon2 or bcrypt-directly; the payment steps are simulated. Naming
   weaknesses + a mitigation plan reads as senior behavior.
